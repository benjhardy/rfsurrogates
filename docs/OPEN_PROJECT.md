# Project design

Version 0.1, 2026-10-26. How the project is organised and why. Numbers come from files in this repo.

## Concept

A surrogate model of a passive microwave device maps a geometry vector p to its S-parameters over a frequency band
in milliseconds instead of minutes, and an optimiser can invert it to find a geometry for a spec. Training one needs
a few hundred full-wave solves per device family: a weekend of compute for one person, little for a group. This
project pools that compute. Anyone can simulate designs of a registered family with their own solver on their own
machine, pass each result through one checker, and submit a compact record. The repo holds the family definitions,
the checker, the trainer and the data index. Hugging Face holds the weights and the records.

## Decisions (v0.1)

| topic | decision |
|---|---|
| repos | one code repo, `github.com/benjhardy/rfsurrogates`; weights in one Hugging Face model repo per family (`rfsurrogates/<family>`); records in one dataset repo (`rfsurrogates/samples`); manifests in git |
| licences | code and weights Apache-2.0 (explicit patent grant); records and data index CC-BY-4.0 |
| scope | one trained model per family, shared code. A model shared across families is a research question (v0.3), reported whether it works or not |
| contributions | data pull requests open with v0.2, after the checker runs in CI; code contributions now; DCO sign-off, no CLA |
| retraining | per release, run by a maintainer, when a family has about 25 % more records or a new fidelity group |
| other solvers | accepted as fidelity group `other`; no published per-solver or solver-vs-solver accuracy (`docs/FIDELITY.md`) |
| front page | the browser demo at `benjhardy.github.io/filter-surrogate/`, linked from this repo, the model card and the agent.rf hub |

## Device family

A family is one entry in `families.json` plus a folder `families/<family_id>/`:

1. `family_id`: a short stable string (`edge_coupled_bpf`).
2. **Generator**: p -> CAD + mesh + solver config for the reference solver, with a geometry gate that rejects a
   layout before a solve starts (`build_case.py`).
3. **Analytic prior**: p, f -> S from textbook formulas (`prior.py`). The network learns a correction to it.
4. **Box**: parameter ranges, units, substrate, centre (`samples.json`).
5. **Validity rule**: a cheap function of p that says whether the layout is the intended device (`family.py`).
6. **Metrics**: what f0, bandwidth, insertion loss and return loss mean for this family.
7. **Frequency grid and ports**: in `families.json`.
8. **Fidelity tags**, the production fidelity and the holdout fidelity (`docs/FIDELITY.md`).

`registry.load_family(family_id)` returns all of it; the checker and the tools use only that interface.

Limit: family modules import their siblings by plain name (`import design`), so one process works with one family
(`RFS_FAMILY`). The second family needs these imports made package-relative.

## Data layers

| layer | what | where |
|---|---|---|
| raw solver runs | mesh, config, logs, fields, port files | stay with the contributor; the record keeps the mesh statistics and the hashes so a run can be audited on request |
| record | p, frequency grid, S11 and S21, solver, version, fidelity, mesh statistics, port, compute, contributor, licence, content hash; about 12 kB per record | npz in the Hugging Face dataset, `<family_id>/<folder>/<id>.npz` |
| data index | one manifest row per record: metadata, checker verdict, hashes, split, path | `data_index/<family_id>/manifest.jsonl` in git |
| weights | ensembles per family, stage-A start point, `weights.json` for the browser, held-out predictions | Hugging Face model repo per family, with a generated model card |
| results | metrics, learning curve, fidelity holdouts | `families/<family_id>/results/` in git, regenerated by a retrain |

## What the learning curve says about the prior

For `edge_coupled_bpf` (26 held-out designs): with the prior the passband error is 1.83 dB at 10 training samples,
0.82 dB at 50 and 0.54 dB at 209; without it 9.49, 1.31 and 0.34 dB. The prior helps below about 50 samples and the
model without it is better from about 100. For a contributed-data project: a new family is useful from its first
few dozen samples if it has a prior, and both variants are trained and published once it has a few hundred.

## Roadmap

1. **v0.1** (done locally): repo, registry, checker, records and manifest, weights and model card, staging and
   fetch tools, browser page.
2. **v0.2**: the checker in CI on data pull requests (download the submitted files, compare the hashes, rerun the
   verdicts); data contributions open; hairpin band-pass filter as the second family (folded resonators, the same
   coupled-line prior and metrics; a cost estimate before any solve); family imports made package-relative.
3. **v0.3**: shared-trunk experiment across the two filter families; stage C (a second substrate, about 30 samples,
   adapted vs from scratch).
4. Later candidates with analytic priors: stepped-impedance low-pass filter, Wilkinson divider and branch-line
   coupler (N-port records: the contract and the trainer grow to full S matrices).

## The browser page

`web/` runs the trained surrogate in the browser: `surrogate.js` is a dependency-free port of the prior and of the
DeepONet forward pass; `weights.json` (from the Hugging Face model repo, or `core/export_web.py`) holds the 5
stage-B and 5 scratch seeds. A visitor sets the geometry inside the box, sees S11 and S21 with the seed spread,
compares with stored Palace curves, and runs inverse design. `web/check_port.mjs` checks the port against Python
(prior to 1e-9, ensemble to 1e-4 dB).
